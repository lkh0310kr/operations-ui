# Component: ValueDisplay, AlarmEntry and AlarmList

`ValueDisplay` presents caller-formatted `Label`, nullable `ValueText`, `Unit`, `RangeText`, `QualityText`, `FreshnessText` and `TimestampText`. It shows a dash for null rather than substituting zero. Quality, freshness and observation time are separate text properties; the control does not determine whether a value is stale or trustworthy. The application owns numeric formatting, units, time zones, sampling and freshness policy. It is non-interactive and does not take Tab focus. Its automation peer exposes a text name assembled from the current properties unless the caller supplies an explicit automation name. Text wraps where the layout has finite width; a consuming screen should provide concise localized descriptions and enough space. The typeface's tabular numeral support and actual screen-reader announcement of changes remain unverified.

Example: `<ui:ValueDisplay Label="압력" ValueText="−12.5" Unit="kPa" QualityText="품질: 양호" FreshnessText="최신성: 오래됨" TimestampText="마지막 수신 10:24:00" />`. For no value, leave `ValueText` null and explain the reason in quality and freshness text. Do not pass an empty string when a visible missing-value marker is required.

`AlarmEntry` renders separate `Title`, `IdentifierText`, `SeverityText`, `ActiveText` and `AcknowledgementText`. `Tone` affects the supplemental marker only and does not infer any domain state. An optional `AcknowledgeCommand`, `AcknowledgeCommandParameter`, `AcknowledgeLabel` and `AcknowledgeHelp` expose an application-owned action. With no command the button is hidden; when a command cannot execute, the application must provide an adjacent reason in `AcknowledgeHelp`. The button retains WPF command, keyboard and CanExecute behavior. The control never clears an alarm, changes acknowledgement, starts sound, blinks or dismisses itself. Its group automation name is composed from the current descriptions unless explicitly supplied. Long descriptions wrap; screen-reader event announcements still require validation.

`AlarmList` is an `ItemsControl` accepting `AlarmEntry` children or data items with a consumer-supplied `ItemTemplate`; the consumer provides ordering, collection updates, an accessible list name and empty/error presentation. Its default items panel is not a data-virtualized alarm store and should not be used to claim performance for an unbounded alarm history. Acknowledgement must not be used as evidence that the source condition has cleared.

The HMI and Component catalog use these same resources. On Windows, `dotnet build VisionApp.Dev.slnx --no-restore` passed without warnings or errors. `--verify-hmi` ran against WPF in Dark and Light and checked the missing-value and independent quality/freshness automation name, alarm title binding, separate active and acknowledgement descriptions, supplied command wiring, and that the sample acknowledgement leaves the sample alarm active. These are programmatic checks, not a screen-reader, keyboard, touch or device test. `hmi-operational.png` and `catalog-operational.png` are WPF captures.
